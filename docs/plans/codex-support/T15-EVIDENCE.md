# T15 Codex executor contract — evidence

T15 defines an offline contract only. `engine/cld_providers/codex/contract.py` checks installed CLI capabilities, builds a fresh explicit `codex exec --json --ephemeral` invocation with stdin and a restricted sandbox, and parses JSONL completion/failure/usage events. It is deliberately unregistered; T16 owns process wiring, candidate acceptance, live canary and four-provider bundle integration. The fixtures are labeled synthetic, not live Codex output. No authenticated Codex executor call was made.

The [official non-interactive guide](https://learn.chatgpt.com/docs/non-interactive-mode), [CLI command reference](https://learn.chatgpt.com/docs/developer-commands), and [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) were checked on 2026-09-25. Installed Windows `codex-cli 0.155.1` returned the required exec flags and stdin `-` behavior, and the new capability check passed directly against its version/help output. This establishes one observed compatibility point, not a universal minimum or entitlement proof. WSL is not installed, so no local Linux CLI probe was possible; the offline contract tests are running in Windows/Ubuntu CI.

The exact selected dogfood model was `opencode:opencode/kimi-k3` (listed by OpenCode 1.18.29). A committed one-slice CLD plan and 18 red acceptance cases were prepared before dispatch. Two initial preflights failed before implementation: the first placeholder raised `NotImplementedError`, which CLD correctly rejected as a non-assertion baseline; the second test's parameter ID contained an authentication phrase that the process classifier interpreted as an auth error. The red-test node IDs were shortened without weakening the stderr-auth case. The third preflight passed. The first validation probe reported 50,148 tokens and USD 0.0524136; no model substitution occurred.

Kimi's isolated candidate passed the 18 focused cases but began an unrequested full offline suite and hit the bounded 600-second process deadline before emitting final JSONL usage. CLD retained its worktree and **did not accept the candidate**; the production attempt's usage and cost are unknown and the ledger blocks further budget admission under `unknown=deny`. The lead reviewed and applied only the candidate's `contract.py` diff to the branch, fixed a real wrapped-help incompatibility found with installed `codex exec --help`, and tightened missing-return-code, stderr-auth, event-order and usage validation. Two additional tests cover those gaps. The 20 focused T15 cases pass. A duplicate local full-suite run was interrupted while progressing to avoid repeating the same broad check already running in CI. Source/test/SOURCES commit: `63b5ed1`; [four-job CI](https://github.com/jhesham/cross-llm-delivery/actions/runs/36102993135) passed full offline tests on Windows/Ubuntu Python 3.11/3.14, both host generators, tracked plugin freshness, Codex package smoke and catalog checks.

The T15 limitation is deliberate: live `codex exec` behavior, model/effort entitlement, authenticated JSONL events, usage fidelity, and POSIX CLI support are unverified until T16. The contract never treats final prose or file-change events as acceptance authority; T16 must use the existing independent Git candidate gate. T16 remains optional and unstarted. T18 is the next required task; stop at this T15 checkpoint until the user confirms token availability.
