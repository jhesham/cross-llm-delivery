## Assessment

The changes address useful operational problems, and the published test and
packaging matrix is green. However, the new worktree garbage collector needs
safety fixes before applying it to retained delivery work. Two reproduced cases
can remove unfinished or actively owned worktrees. Validation context filtering
also misses legitimate account changes, and network failures after long output
still trigger retries.

The following findings are open. P1 means high priority because unfinished work
can be deleted; P2 means a conditional correctness or operational defect.
All reproductions used disposable local repositories or injected offline process
fixtures. No production worktree was removed.

## Findings and corrective tasks

### R01 — P1: colliding slice slugs can delete another slice's unfinished work

Location: `engine/cld/gc.py:69`, `engine/cld/gc.py:90`.

GC reduces the ledger to a dictionary keyed by the sanitized, truncated slice
slug. Valid IDs `A.B` and `A_B` both become `A_B`; IDs sharing their first 40
characters also collide. The last ledger entry overwrites the other status.
GC then treats every matching worktree as belonging to that entry, without
using the session's original slice identity.

Reproduction: both IDs passed plan validation. With `A.B = needs_repair` and
`A_B = integrated`, GC selected the dirty `A.B` worktree for removal, reported
"slice integrated", and successfully force-removed it. The files were gone.
The current-build path does not perform the earlier-build dirty check.

- [x] Resolve the original slice ID from matching run/session recovery evidence,
      validating its repository, ledger and worktree identity.
- [x] Fail closed on ambiguous or missing identity; do not infer ownership from
      the slug alone.
- [x] Add real-Git tests for dot/underscore and truncation collisions, including
      unfinished changes in the retained slice.

### R02 — P1: previous-build cleanup bypasses active ownership

Location: `engine/cld/cli.py:803`, `engine/cld/cli.py:817`,
`engine/cld/gc.py:72`.

The writer lock covers only the selected ledger. `--include-previous` considers
every other run under the root eligible when Git status is clean, regardless of
whether another ledger is dispatching into it. It never acquires the existing
repository-wide slice ownership lock or verifies another run is inactive.
A newly created executor worktree can be clean while its process is running.
The registry lock only serializes Git add/remove operations, not execution.

Reproduction: held another ledger's writer lock and `slice_owner(repo, "A")`,
then ran `_gc_report` through a separate ledger with apply/include-previous.
GC exited zero and deleted the worktree while both ownership locks were held.

- [x] Establish ownership for each candidate before deciding and removing it;
      keep candidates with active or unverifiable owners.
- [x] Cover slice and integration worktrees, including simultaneous builds using
      different ledger files or linked checkouts.
- [x] Recheck eligibility under ownership at removal time to prevent changes
      between the status check and forced removal.
- [x] Add a competing-owner real-Git test which requires GC to retain the tree.

### R03 — P2: OpenCode account changes do not invalidate validation evidence

Location: `engine/cld_providers/opencode/provider.py:369`,
`engine/cld/admission.py:46`.

The new environment filter selects only `OPENCODE_*` and shared proxy/TLS
variables for OpenCode. OpenCode configuration can reference other environment
variables, including `ANTHROPIC_API_KEY`, through `{env:VARIABLE}`. Hashing the
unchanged configuration file hashes the placeholder, not its resolved value.
This regresses the former complete-environment fingerprint: an account or
endpoint change can reuse evidence for the previous configuration.

Reproduction: an unchanged config with
`"apiKey": "{env:ANTHROPIC_API_KEY}"` produced the same fingerprint for two
different synthetic credential values. The credential name was not selected.
OpenCode documents this exact substitution mechanism in its
[configuration reference](https://opencode.ai/docs/config/#env-vars).

- [x] Include the selected backend's authentication/routing variables and
      variables referenced by configuration, while excluding unrelated lead
      session variables.
- [x] Hash values without recording secrets in evidence or diagnostics.
- [x] Add account/endpoint-change tests alongside the existing unrelated-session
      stability tests. Include custom variable names used in configuration.

### R04 — P2: GC accepts a ledger bound to a different repository

Location: `engine/cld/cli.py:801`.

Unlike `_load_ledger_or_blocked` and delivery's build validation, `_gc_report`
does not compare `ledger.build.repo` or its common Git directory with `--repo`.
Its lock and current-run identity can therefore come from repository A while
it discovers and deletes worktrees from repository B. A wrong explicit ledger
path is especially dangerous with `--include-previous`.

Reproduction: created a valid schema-2 ledger bound to A, passed it to GC with
`repo=B`, apply and include-previous. GC returned zero and removed B's worktree
instead of rejecting the repository mismatch.

- [x] Validate repository and common-Git-directory identity before discovery or
      mutation, using the same binding rules as delivery.
- [x] Add text/JSON CLI tests asserting mismatch blocks without removals.

### R05 — P2: ignored files can be deleted despite the clean-worktree safeguard

Location: `engine/cld/gc.py:61`, `engine/cld/gc.py:78`;
forced removal occurs in `engine/cld/worktree.py:104`.

`git status --porcelain` omits ignored files. GC interprets an otherwise clean
previous worktree containing ignored local data as having no uncommitted
changes, then removes it with `--force`. Preserving recovery refs does not
preserve ignored data that was never added to a recovery tree.

Reproduction: an earlier worktree contained an ignored `cache/retained.db`.
`worktree_dirty` returned false; GC selected removal and deleted that file and
the worktree. This is distinct from R02: it occurs without concurrent writers.

- [x] Detect ignored files before declaring a previous worktree safe to remove.
- [x] If expected disposable tool caches may be removed, define an explicit,
      narrow discard policy and expose it in preview; retain unknown ignored
      files rather than silently force-removing them.
- [x] Test ignored local data separately from disposable generated caches.

### R06 — P2: late network errors still retry and can escalate

Location: `engine/cld/orchestrator.py:195`;
bounded log construction in `engine/cld_providers/codex/provider.py:195`
and `engine/cld/process.py:277`.

The orchestrator searches `result.raw_log` for network failures. That log is
bounded to 4,000 characters and keeps the beginning of output. Codex concatenates
stdout before stderr, so an error on stderr or at the end of a long event stream
can be absent from the classified text. The complete streams are retained, but
are not used for classification.

Reproduction: injected more than 4,000 characters of ordinary stdout followed
by `getaddrinfo ENOTFOUND` on stderr and `nonzero_exit`. Delivery returned
`final_error=None` and dispatched three times. The short-log fixture correctly
stops once; the long-log case defeats the new behavior.

- [x] Classify network failures from complete retained output or structured
      provider errors before truncating user-facing feedback.
- [x] Preserve the existing guard that successful dispatches mentioning a
      recovered network failure must not be classified as failed.
- [x] Add adapter-to-orchestrator tests for long stdout plus failing stderr and
      a terminal failure event, asserting one dispatch and no escalation.

### R07 — P2, narrower adapter case: custom Git runners disable native launching

Location: `engine/cld_providers/codex/provider.py:98`,
`engine/cld_providers/codex/provider.py:150`.

Native Codex resolution is enabled only if both the process runner and Git
runner are the defaults. Supplying a custom Git runner disables native
resolution even when Codex execution uses the production process runner.
Git diff injection should not determine how the Codex executable is launched.
On an npm-only Windows installation this restores the original shim-launch
failure. The ordinary CLI path using both defaults is unaffected.

Offline reproduction: retained production-runner identity, injected only the
Git runner, and supplied a native resolver fixture. The resolver was never
called and the first probe still used logical `codex`, yielding missing_binary.

- [x] Gate native resolution on the process runner's identity alone, preserving
      wholly injected process fixtures without coupling to Git injection.
- [x] Add an npm-only launch test with production execution and custom Git runner.
