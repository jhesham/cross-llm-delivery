## N01 — P1: inherited Claude effort overrides the user's explicit selection

Locations: `engine/cld_providers/claude/contract.py:132`,
`engine/cld_providers/claude/contract.py:21`,
`engine/cld_providers/claude/provider.py:174`.

The invocation passes `--effort low` for a low-effort executor, but the child
inherits `CLAUDE_CODE_EFFORT_LEVEL`. It is neither overridden nor removed.
Claude Code explicitly documents that this variable takes precedence over
`--effort`. A lead launched with `CLAUDE_CODE_EFFORT_LEVEL=max` therefore changes
the executor's actual effort while CLD still identifies it as `@low`.

That variable is also absent from the validation environment patterns.
Evidence obtained with one ambient effort remains current after it changes.
This undermines exact effort selection, usage expectations and evidence identity;
it does not demonstrate a bypass of the engine's aggregate budget checks.

Offline reproduction:

1. Build an invocation for `claude-sonnet-5`, effort `low`.
2. Run a model-free child through the shared `run_process`, using the invocation's
   env and unset_env, with a synthetic parent `CLAUDE_CODE_EFFORT_LEVEL=max`.
3. The child reads `max`, although argv specifies `low`.
4. Context fingerprints for ambient `low` and `max` are identical.

CLI precedence is confirmed by the official
[environment reference](https://code.claude.com/docs/en/env-vars#precedence).
No live Claude inference was used; the resulting effort is inferred from the
documented precedence and the reproduced child environment.

- [x] Pin the effective child effort to the selected spec, preferably overriding
      the inherited environment variable with the selected value.
- [x] Ensure admission identity describes the effective configuration; hash any
      remaining ambient controls that can affect it, without restoring unrelated
      lead session variables to the fingerprint.
- [x] Add an invocation/shared-process test with inherited max and selected low,
      plus a context test. Keep explicit max possible when selected by the user.

## N02 — P2: production nonzero-exit metadata masks login and usage-limit errors

Location: `engine/cld_providers/claude/contract.py:164`.

`parse_result` returns immediately for any non-None process_error. The shared
production runner supplies `nonzero_exit` for an ordinary exit code 1. That
prevents the parser from inspecting the CLI's login/usage-limit diagnostics and
returning the new final errors `not_logged_in` or `usage_limit`.

The new tests supply an exit code and diagnostic but leave process.error unset,
so they test a different boundary from production. This is particularly relevant
when a subscription limit is reached after preflight, or authentication expires
during execution.

Offline reproduction:

- A real model-free subprocess prints `Not logged in. Please run /login` or
  `You are out of extra usage` to stderr and exits 1.
- The shared runner reports `nonzero_exit`; `parse_result` retains that generic
  error instead of the intended final classification.
- Feeding the same process metadata through the Claude adapter and orchestrator
  dispatches **three times**, with `final_error=None`, for each diagnostic.

Consequently delivery retries and can escalate or end in a repair/failure state
instead of stopping once at the resumable gate 5. The reproduction does not
claim these failed attempts consumed inference tokens.

- [x] Keep actual lifecycle failures (timeout, cancellation, missing executable,
      etc.) authoritative, but inspect provider diagnostics when process_error
      is the generic nonzero-exit classification.
- [x] Never accept a nonzero exit as a successful candidate.
- [x] Add real-runner parser and adapter-to-orchestrator tests requiring one
      dispatch, the intended final error, and no escalation.

## N03 — P2: inline OpenCode configuration bypasses the R03 context fix

Locations: `engine/cld_providers/opencode/provider.py:378`,
`engine/cld/cli.py:629`.

The new config_env hook extracts `{env:NAME}` references from file paths only.
OpenCode also supports inline configuration through `OPENCODE_CONFIG_CONTENT`.
CLD fingerprints that variable's literal contents because it matches
`OPENCODE_*`, but does not fingerprint the values referenced inside it.

Reproduction: hold inline JSON constant with an API key reference
`{env:MY_GATEWAY_KEY}` and base URL reference `{env:MY_GATEWAY_URL}`. Change both
synthetic variables. The validation context fingerprint stays identical.
The changed account/endpoint can therefore reuse prior validation evidence.

OpenCode documents the inline configuration source and environment substitution
in its [configuration reference](https://opencode.ai/docs/config/).
The file-based credential case from the previous review is fixed; the broader
R03 claim remains incomplete for this supported configuration source.

- [x] Extract referenced names from inline config as well as every supported
      configuration source CLD admits.
- [ ] Include relevant backend credential/routing variables even when not named
      with the `OPENCODE_*` prefix; retain secret hashing and avoid diagnostics
      containing values.
- [x] Test changing an inline-referenced key and endpoint independently, and
      preserve the unrelated-session stability test.
